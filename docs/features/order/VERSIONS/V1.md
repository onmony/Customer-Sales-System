# Order V1

## Purpose

Define minimum order capability for Phase 1 customer-to-invoice workflow.

This document is the source of truth for Order V1 business rules. Technical documents must reference these rules instead of redefining them.

## Included Scope

- Create order for selected customer.
- Add products as order items.
- Resolve pricing for order items.
- Save order with immutable pricing snapshots.
- Preserve complete order document payload.
- Prepare order for invoice creation.
- Enforce tenant isolation.
- Preserve customer, product, and pricing snapshot context required by downstream documents.

## Excluded Scope

- Warehouse allocation.
- Shipment planning.
- Delivery confirmation.
- Payment collection.
- Approval workflows.
- Returns.
- Backorders.
- Partial fulfillment.
- Order discounts.
- Tax calculation.
- Credit checks.
- Order import.

## Business Rules

### ORD-1 Tenant Scope

Every order belongs to exactly one tenant.

Orders from one tenant must not be visible, searchable, selectable, or usable by another tenant.

### ORD-2 Customer Required

An order must have a customer.

The customer must belong to the same tenant as the order.

### ORD-3 Order Creation From Customer

Order creation starts from a selected customer.

### ORD-4 Items Required

An order must have at least one order item before it can be saved.

### ORD-5 Product Required

Every order item must reference a product.

The product must belong to the same tenant as the order.

### ORD-6 Quantity Required

Every order item must have a quantity.

Quantity validation rules are not finalized in V1.

### ORD-7 Pricing Resolution Required

Every order item must have pricing resolved according to the Pricing module before the order can be saved.

### ORD-8 Pricing Snapshot Required

Every saved order item must include an immutable pricing snapshot.

### ORD-9 Customer And Product Snapshot Safety

Saved orders must preserve customer and product context required by downstream immutable documents.

### ORD-10 Historical Safety

Saved order pricing must not change when customer pricing changes later.

Saved order customer and product context must not be rewritten by later customer or product changes.

### ORD-10A Order Document Payload

Every order owns a complete `orderDocumentPayload` JSONB business document payload.

Draft orders may regenerate the payload whenever the order changes.

Confirmed orders freeze the payload forever.

Order rendering must use `orderDocumentPayload`.

### ORD-11 Invoice Readiness

An order is eligible for invoice creation only after it is saved with required item and pricing snapshots.

### ORD-12 Draft, Edit, Status, And Cancellation Policy

Draft, edit, status, locking, and cancellation behavior is not finalized in V1.

The system must not invent these policies during implementation.

### ORD-13 Module Boundary

Order coordinates selected customers, products, quantities, pricing snapshots, and invoice readiness. It does not define pricing calculation, customer identity rules, product identity rules, invoice immutability, warehouse allocation, shipment, delivery, payment, or accounting behavior.

## Acceptance Criteria

- A user can create an order from a customer.
- A user can add products to the order.
- Pricing resolves for each order item according to Pricing documentation.
- Saved order items preserve pricing snapshots.
- Saved orders preserve `orderDocumentPayload`.
- A saved order has at least one item.
- An order without required pricing snapshots cannot be saved.
- Cross-tenant orders, customers, products, and prices are not usable.
- Draft, edit, status, and cancellation behavior remains blocked until approved.

## Open Questions

- Order statuses are not finalized.
- Saved order edit policy is not finalized.
- Order cancellation policy is not finalized.
- Draft order behavior is not finalized.
- Quantity validation rules are not finalized.
- Order numbering policy is not finalized.
- Order locking policy is not finalized.
- Order-level discount policy is not finalized.
